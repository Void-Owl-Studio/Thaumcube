# Агентская инструкция для разработки Minecraft-like игры

Этот документ определяет обязательные правила для любого агента, который пишет код в проекте.

## 1. Общие инженерные принципы

1. Не создавать спагетти-код.
2. Не писать неоптимизированный код, если можно сразу реализовать более эффективное и читаемое решение без чрезмерного усложнения.
3. Всегда следить за принципами ООП там, где проектная архитектура действительно выигрывает от объектной модели.
4. Всегда проверять код на наличие ошибок до завершения задачи.

## 2. Архитектурные правила

1. Разделять ответственность между классами, модулями и системами.
2. Не смешивать генерацию мира, рендеринг, физику, ввод, UI и сохранение данных в одном классе.
3. Каждый класс должен иметь одну основную ответственность.
4. Предпочитать расширяемую архитектуру вместо жёстко связанных решений.
5. Зависимости между системами должны быть явными и минимальными.
6. Избегать глобального состояния, если оно не оправдано архитектурой движка.
7. Новую функциональность добавлять через отдельные компоненты, сервисы, менеджеры или системы, а не через разрастание одного файла.

## 3. Требования к качеству кода

1. Код должен быть читаемым, предсказуемым и поддерживаемым.
2. Имена классов, методов, переменных и файлов должны ясно отражать назначение.
3. Не дублировать логику. Повторяющийся код выносить в общие абстракции или утилиты.
4. Не использовать "магические числа" без констант или понятного контекста.
5. Сложные участки сопровождать короткими и полезными комментариями.
6. Любое решение должно быть понятно следующему разработчику без долгой расшифровки намерений.

## 4. Производительность

1. Учитывать производительность как часть базовой реализации, а не как позднюю доработку.
2. Избегать лишних аллокаций, особенно в часто вызываемых циклах обновления мира, генерации чанков и рендеринга.
3. Не пересчитывать данные каждый кадр, если их можно кешировать.
4. Использовать чанковую архитектуру для мира, а не работать с вокселями глобально как с единым массивом.
5. Выполнять генерацию, пересборку мешей и тяжёлые вычисления по возможности асинхронно или батчами.
6. Ограничивать радиус загрузки, генерации и обновления мира вокруг игрока.
7. Проверять узкие места: генерация чанков, построение мешей, освещение, коллизии, сохранение и загрузка.

## 5. Правила ООП

1. Соблюдать инкапсуляцию: внутреннее состояние объекта не должно свободно ломаться внешним кодом.
2. Использовать наследование только там, где действительно есть отношение "является".
3. Предпочитать композицию наследованию, если это уменьшает связанность.
4. Проектировать интерфейсы и абстракции для систем генерации, хранения, рендеринга и взаимодействия с блоками.
5. Не превращать классы в "божественные объекты", которые знают обо всём проекте.
6. Логику поведения держать рядом с соответствующей сущностью или системой, а не размазывать по случайным менеджерам.

## 6. Проверка ошибок и надёжность

1. Перед завершением задачи агент обязан проверить код на очевидные ошибки, регрессии и конфликтующие зависимости.
2. Любая новая система должна корректно обрабатывать невалидные входные данные, отсутствующие ресурсы и пограничные случаи.
3. Нельзя молча игнорировать ошибки там, где они влияют на стабильность мира или сохранений.
4. Для критичных операций добавлять защитные проверки, логирование и понятные сообщения об ошибках.
5. При изменении генерации мира, формата чанков или сохранений учитывать обратную совместимость либо явно фиксировать миграции.

## 7. Правила для Minecraft-like игры

1. Весь мир должен строиться вокруг чанков как основной единицы хранения, генерации, загрузки, выгрузки и сохранения.
2. Размер чанка должен быть фиксированным и использоваться единообразно во всех системах.
3. Данные чанка должны быть отделены от его визуального представления.
4. Логика блока, данные блока и рендер-представление блока не должны быть слиты в одну неразделимую структуру.
5. Системы разрушения, размещения, освещения, жидкостей и обновления соседей должны проектироваться так, чтобы их можно было развивать независимо.
6. Генерация мира должна быть детерминированной при одинаковом seed.
7. Любые изменения мира игроком должны применяться поверх базовой процедурной генерации, а не ломать её модель.

## 8. Правила для voxel generation system

1. Генерация должна быть многослойной:
   - базовый шум рельефа;
   - биомы;
   - поверхностные блоки;
   - пещеры;
   - карта температуры;
   - структуры;
   - локальные модификаторы.
2. Каждый этап генерации должен быть отдельной системой или модулем с чётким контрактом.
3. Генератор не должен напрямую зависеть от рендера или UI.
4. Использовать seed, координаты чанка и мировые координаты как основу детерминированных вычислений.
5. Не хранить весь мир в памяти целиком. Загружать и генерировать только нужные чанки.
6. При генерации избегать повторного вычисления уже готовых данных чанка без причины.
7. Все дорогие операции, связанные с мешами чанков, должны запускаться только при реальных изменениях содержимого.
8. Для мешинга использовать отсечение невидимых граней как базовый минимум.
9. Если проект дойдёт до этапа оптимизации, предусмотреть переход на greedy meshing или аналогичную технику уменьшения числа полигонов.
10. Обновление соседних чанков при изменении блоков на границе должно быть обязательной частью системы.
11. Генерация чанков должна безопасно работать в очередях задач и не ломаться при быстрой загрузке и выгрузке мира.
12. Система сохранения должна хранить только необходимые данные:
   - seed мира;
   - метаданные мира;
   - изменённые чанки или дельты;
   - данные игрока и сущностей.

## 9. Рекомендованная структура систем

Минимально желательно разделять проект на такие зоны ответственности:

1. `WorldManager` или эквивалентная система управления миром.
2. `ChunkManager` для загрузки, выгрузки и отслеживания чанков.
3. `ChunkData` для хранения блоков.
4. `ChunkGenerator` для процедурной генерации.
5. `ChunkMeshBuilder` для построения мешей.
6. `BlockRegistry` для описания типов блоков и их свойств.
7. `SaveSystem` для сохранения и загрузки.
8. `PlayerController` отдельно от логики мира.
9. `BiomeSystem` или эквивалент для биомов.
10. `StructureGenerator` для деревьев, руд, построек и других структур.

## 10. Что агенту запрещено

1. Запихивать всю логику мира в один класс или один файл.
2. Делать прямую связку "игрок -> генерация -> мешинг -> рендер" без промежуточных абстракций.
3. Писать код "на будущее", который не нужен текущей задаче, если он усложняет архитектуру.
4. Жертвовать читаемостью ради микровыигрыша в производительности без подтверждённой причины.
5. Проводить опасные рефакторы без проверки влияния на генерацию, сохранения и границы чанков.
6. Оставлять TODO вместо исправления критичных ошибок, если задача предполагает рабочий результат.

## 11. Обязательный рабочий процесс агента

1. Перед реализацией кратко определить, к какой системе относится задача.
2. Проверить, не нарушает ли решение чанковую архитектуру и разделение ответственности.
3. После изменений проверить:
   - компиляцию;
   - очевидные ошибки выполнения;
   - граничные случаи;
   - влияние на соседние чанки;
   - влияние на сохранение и загрузку.
4. Если есть риск деградации производительности, кратко отметить это и предложить безопасный путь оптимизации.

## 12. Приоритеты при принятии решений

1. Корректность.
2. Поддерживаемость.
3. Производительность.
4. Расширяемость.
5. Удобство дальнейшей отладки.

Если между скоростью написания и качеством архитектуры есть конфликт, выбирать решение, которое не создаёт технический долг без необходимости.
